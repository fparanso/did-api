# v1.2 Design Spec — Email Auth + Organizations

**Date:** 2026-05-23
**Branch:** `feat/v1.2-email-auth`
**Status:** Approved

---

## Overview

v1.2 adds two tightly coupled subsystems on top of the existing DID + ZKP engine:

1. **Email/password authentication** — users sign up with email + password; the server auto-creates a `subject` DID on their behalf. They receive a JWT identical in shape to the one issued by DID-auth, so all existing protected endpoints work without change.

2. **Organizations** — users can create organizations. Each org gets its own DID (as a first-class cryptographic actor) and a three-tier membership system (owner / admin / member). Members can be invited by email or DID address.

The existing DID challenge/response auth flow (`POST /v1/auth/challenge` + `POST /v1/auth/verify`) is **kept unchanged** for backward compatibility and power users.

**Delivery:** Two implementation milestones in one spec/plan cycle:
- **Milestone 1:** Email auth (signup, login, password reset, admin role upgrade, user profile)
- **Milestone 2:** Organizations (create, invite, manage, delete)

### Dependency Flow

```
auth/routes → users/service (login)
users/routes → users/service → users/repository
                             → did/service (createDid on signup)
                             → auth/service (issueJwt)
organizations/routes → organizations/service → organizations/repository
                                             → did/service (createDid for org DID)
                                             → auth/service (issueJwt — reused)
```

No circular dependencies. `did/service` and `auth/service` are shared utilities; both new domains import from them explicitly.

## Data Model

### Migration `003_users.sql`

```sql
CREATE TABLE IF NOT EXISTS users (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  email             TEXT NOT NULL UNIQUE,
  password_hash     TEXT NOT NULL,
  name              TEXT NOT NULL,
  organization_name TEXT,
  did               TEXT NOT NULL REFERENCES dids(id),
  created_at        TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS users_email_idx ON users (email);

CREATE TABLE IF NOT EXISTS password_reset_tokens (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  user_id     UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  token       TEXT NOT NULL UNIQUE,   -- 32-byte cryptographically random, hex-encoded
  expires_at  TIMESTAMPTZ NOT NULL,   -- 1-hour TTL
  used        BOOLEAN NOT NULL DEFAULT false,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX IF NOT EXISTS prt_token_idx ON password_reset_tokens (token);
CREATE INDEX IF NOT EXISTS prt_user_idx  ON password_reset_tokens (user_id);
```

### Migration `004_organizations.sql`

```sql
CREATE TABLE IF NOT EXISTS organizations (
  id          UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  name        TEXT NOT NULL,
  slug        TEXT NOT NULL UNIQUE,
  did         TEXT NOT NULL REFERENCES dids(id),
  owner_id    UUID NOT NULL REFERENCES users(id),
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE TABLE IF NOT EXISTS org_members (
  org_id      UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  user_id     UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  role        TEXT NOT NULL CHECK (role IN ('owner', 'admin', 'member')),
  joined_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  PRIMARY KEY (org_id, user_id)
);

CREATE TABLE IF NOT EXISTS org_invites (
  id           UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id       UUID NOT NULL REFERENCES organizations(id) ON DELETE CASCADE,
  invited_by   UUID NOT NULL REFERENCES users(id),
  email        TEXT,
  did          TEXT,
  role         TEXT NOT NULL CHECK (role IN ('admin', 'member')),
  token        TEXT NOT NULL UNIQUE,
  accepted     BOOLEAN NOT NULL DEFAULT false,
  expires_at   TIMESTAMPTZ NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now(),
  CHECK (email IS NOT NULL OR did IS NOT NULL)
);

CREATE INDEX IF NOT EXISTS org_members_user_idx ON org_members (user_id);
CREATE INDEX IF NOT EXISTS org_invites_email_idx ON org_invites (email);
CREATE INDEX IF NOT EXISTS org_invites_did_idx ON org_invites (did);
CREATE INDEX IF NOT EXISTS org_invites_token_idx ON org_invites (token);
```

### Key Design Decisions

| Decision | Rationale |
|----------|-----------|
| `org_members` composite PK `(org_id, user_id)` | One role per user per org, enforced at DB level. A user can be a member of unlimited organizations simultaneously. |
| `organizations.did` references `dids` | Org is a first-class cryptographic actor — it can be attested and issue credentials. |
| `organizations.slug` unique | URL-safe handle for human-readable org identification in routes. |
| `org_invites.token` unique | Random secure token for email invite links. DID invites skip this entirely. |
| `CHECK (email IS NOT NULL OR did IS NOT NULL)` | Enforces every invite has a target. |
| No `role` on `users` | Role lives on `dids.role` — single source of truth. |
| No email verification in v1.2 | YAGNI — `verified_at` column can be added in v1.3 if needed. |

## Auth Flows

### Signup — `POST /v1/auth/signup`

**Request:**
```json
{
  "email": "alice@example.com",
  "password": "minimum8chars",
  "name": "Alice Smith",
  "organizationName": "Acme University"
}
```

**Server steps (single DB transaction):**
1. Validate with Zod (email format, password min 8 chars, name non-empty)
2. Check email uniqueness → `409 EMAIL_TAKEN` if duplicate
3. Hash password with **Argon2id** (`memoryCost: 19456`, `timeCost: 2` — OWASP minimum)
4. Call `createDid('subject')` → generates Ed25519 keypair, persists `dids` row
5. Insert `users` row
6. Call `issueJwt(did, 'subject')` → 15-min JWT
7. Insert `sessions` row
8. Write audit log (`action: 'auth'`, `result: 'success'`)

**Response `201`:**
```json
{
  "token": "eyJhbGci...",
  "user": {
    "id": "uuid",
    "email": "alice@example.com",
    "name": "Alice Smith",
    "did": "did:key:z6Mk...",
    "role": "subject"
  }
}
```

> The `privateKey` is **not returned** at signup. The server manages the DID keypair internally. Users authenticate via email/password — they never handle raw key material.

---

### Login — `POST /v1/auth/login`

**Request:**
```json
{ "email": "alice@example.com", "password": "minimum8chars" }
```

**Server steps:**
1. Validate with Zod
2. Look up user by email — if not found, return `401 INVALID_CREDENTIALS` (no leaking)
3. Verify Argon2id hash — if mismatch, return `401 INVALID_CREDENTIALS` (same error)
4. Fetch `dids.role` for the user's DID
5. Call `issueJwt(did, role)` → JWT
6. Insert `sessions` row
7. Write audit log

**Response `200`:**
```json
{
  "token": "eyJhbGci...",
  "user": {
    "id": "uuid",
    "email": "alice@example.com",
    "name": "Alice Smith",
    "did": "did:key:z6Mk...",
    "role": "subject"
  }
}
```

> Both "email not found" and "wrong password" return `INVALID_CREDENTIALS` — prevents email enumeration (OWASP API2).

---

### Forgot Password — `POST /v1/auth/forgot-password`

**Request:**
```json
{ "email": "alice@example.com" }
```

**Server steps:**
1. Validate email format with Zod
2. Look up user by email
   - If **not found**: return `200 OK` with a generic message (no email enumeration)
   - If **found**: continue
3. Invalidate any existing unused reset tokens for this user (`UPDATE ... SET used = true`)
4. Generate a cryptographically secure random token (32 bytes, hex-encoded)
5. Insert `password_reset_tokens` row with **1-hour TTL**
6. Return token in response (consuming app is responsible for delivering it — email sending is out of scope for v1.2)
7. Write audit log

**Response `200` (always — even if email not found):**
```json
{
  "message": "If that email is registered, a reset token has been issued.",
  "resetToken": "a3f9c2..."   // only present if email was found; consuming app sends this via email
}
```

> **Security note:** The response shape is identical whether or not the email exists — clients cannot determine if an account is registered from this endpoint.

---

### Reset Password — `POST /v1/auth/reset-password`

**Request:**
```json
{
  "token": "a3f9c2...",
  "newPassword": "newMinimum8chars"
}
```

**Server steps:**
1. Validate input with Zod (token non-empty, newPassword min 8 chars)
2. Look up token in `password_reset_tokens` → `404 RESET_TOKEN_INVALID` if not found
3. Check `used = false` → `410 RESET_TOKEN_USED` if already consumed
4. Check `expires_at > now()` → `410 RESET_TOKEN_EXPIRED` if stale
5. Hash new password with Argon2id (same params as signup)
6. In a single DB transaction:
   - `UPDATE users SET password_hash = ? WHERE id = token.user_id`
   - `UPDATE password_reset_tokens SET used = true WHERE id = token.id`
   - Invalidate all active sessions for this user: `DELETE FROM sessions WHERE did = user.did`
7. Write audit log (`action: 'auth'`, `result: 'success'`, target: user DID)

**Response `200`:**
```json
{ "message": "Password updated successfully. Please log in again." }
```

> All existing sessions are invalidated on reset — any active JWTs for this user become unusable, forcing a fresh login. This limits the blast radius of a compromised session token.

---

### Admin Role Upgrade — `POST /v1/admin/users/:id/role`

**Headers:** `X-Admin-Secret: <ADMIN_SECRET env var>`
**Request:** `{ "role": "issuer" }`

**Server steps:**
1. Validate `X-Admin-Secret` header matches `ADMIN_SECRET` env var → `401` if mismatch
2. Validate role enum (`subject | issuer | verifier | attester`)
3. `UPDATE dids SET role = ? WHERE id = user.did`
4. Write audit log

| Scenario | Status | Code |
|----------|--------|------|
| Email already registered | `409` | `EMAIL_TAKEN` |
| Email not found at login | `401` | `INVALID_CREDENTIALS` |
| Wrong password | `401` | `INVALID_CREDENTIALS` |
| Password < 8 chars | `400` | `VALIDATION_ERROR` |
| Invalid email format | `400` | `VALIDATION_ERROR` |
| Bad or missing admin secret | `401` | `UNAUTHORIZED` |
| Reset token not found | `404` | `RESET_TOKEN_INVALID` |
| Reset token already used | `410` | `RESET_TOKEN_USED` |
| Reset token expired | `410` | `RESET_TOKEN_EXPIRED` |
| New password < 8 chars | `400` | `VALIDATION_ERROR` |

## Organization Flows

### Create Organization — `POST /v1/organizations`

**Request:**
```json
{
  "name": "Acme University",
  "slug": "acme-university",
  "role": "issuer"
}
```
`slug` is optional — auto-generated from `name` if omitted (lowercased, spaces → hyphens, special chars stripped).
`role` is the org DID's role (`issuer | attester | verifier`).

**Server steps (single DB transaction):**
1. Validate input
2. Auto-generate slug if omitted; check uniqueness → `409 SLUG_TAKEN`
3. Call `createDid(role)` → org gets its own DID + keypair
4. Insert `organizations` row
5. Insert `org_members` row (`user_id = caller`, `role = 'owner'`)
6. Write audit log

**Response `201`:**
```json
{
  "id": "uuid",
  "name": "Acme University",
  "slug": "acme-university",
  "did": "did:key:z6Mk...",
  "memberRole": "owner"
}
```

---

### Invite Member — `POST /v1/organizations/:id/invites`

Requires `admin` or `owner` org role. Supply `email` **or** `did` — not both.

```json
{ "email": "bob@example.com", "role": "member" }
// OR
{ "did": "did:key:z6Mk...", "role": "admin" }
```

**Path A — invite by DID:**
1. Look up user by DID → `404 USER_NOT_FOUND` if not found
2. Check not already a member → `409 ALREADY_MEMBER`
3. Insert `org_members` row directly (instant, no token)
4. Response: `201 { membership record }`

**Path B — invite by email:**
- If email belongs to an existing user → follow Path A (add directly)
- If email is unknown:
  1. Generate cryptographically secure random token (32 bytes, hex-encoded)
  2. Insert `org_invites` row with 72-hour TTL
  3. Response: `201 { "inviteToken": "...", "expiresAt": "..." }` (consuming app is responsible for sending the email)

---

### Accept Invite — `POST /v1/organizations/invites/:token/accept`

Called by a new user after signup, with the token from their invite link.

1. Look up invite by token → `404` if not found
2. Check not expired → `410 INVITE_EXPIRED`
3. Check not already accepted → `409 INVITE_ALREADY_USED`
4. Check caller email matches `invite.email` → `403 FORBIDDEN`
5. Insert `org_members` row
6. Mark `invite.accepted = true`

---

### Manage Members

**`PATCH /v1/organizations/:id/members/:userId` — update role**
```json
{ "role": "admin" }
```
- `owner` can change anyone's role except their own
- `admin` can promote `member → admin` only (cannot create or demote owners)
- Downgrading the last `owner` → `409 CANNOT_REMOVE_LAST_OWNER`

**`DELETE /v1/organizations/:id/members/:userId` — remove member**
- Removing the last `owner` → `409 CANNOT_REMOVE_LAST_OWNER`
- A member can remove themselves from an org (leave)

**`DELETE /v1/organizations/:id` — delete org**
- `owner` only
- Cascades: removes `org_members` + `org_invites` (DB `ON DELETE CASCADE`)
- Org DID is deactivated via existing `deactivate()` service

## Security Controls

| Threat | Control |
|--------|---------|
| Password brute-force | Argon2id hash (OWASP minimum params) + existing 100 req/min rate limit |
| Email enumeration at login | `INVALID_CREDENTIALS` for both bad email and bad password |
| Email enumeration at forgot-password | Always returns `200` with same message shape regardless of whether email exists |
| Reset token guessing | 32-byte cryptographically random token (256-bit entropy), 1-hour TTL, single-use |
| Session fixation after reset | All active sessions deleted when password is reset; user must log in again |
| Stale reset tokens | Previous unused tokens invalidated when a new reset is requested |
| Admin endpoint exposure | `X-Admin-Secret` header required; constant-time comparison to prevent timing attacks |
| Invite token guessing | 32-byte cryptographically random token (256-bit entropy), 72-hour TTL, single-use |
| Org BOLA | All org routes verify caller is a member before any data access |
| Last owner lockout | Service layer blocks removal/demotion of last owner |
| Org DID orphaning | Org deletion deactivates the org DID in the same transaction |

## Out of Scope for v1.2

- Email sending (reset tokens and invite tokens are returned in the API response for integration by the consuming app)
- Email verification (`verified_at` — deferred to v1.3)
- OAuth / social login
- Org-level credential issuance UI (org DID is created and attestable; full workflow is through existing VC endpoints)
- Billing or subscription tiers per org
